# Check Before You Build

NavyLINK's motto is **Create once, discover everywhere, improve together.** The advisor supports it by finding existing capabilities, identifying reuse opportunities and connecting complementary work through approved contacts. Discovery stays within each user's authorized catalog view.

The proposal-analysis agent is a finite local workflow with no external LLM calls or action integration. It executes the application search, registry, related-project, comparison and access tools. Recommendations are deterministic inferences from authorized catalog evidence. They are leads for human review, never a permission grant or confirmed reuse decision. The separate question assistant has optional configured generation, described in `PHASE2.md`.

## Execution

1. Extract mission concepts from the submitted mission problem, description, intended solution and desired capabilities. Only a mission problem or description is mandatory.
2. Run real hybrid retrieval against authorized records (maximum 12 initial results).
3. Follow related-project connections from at most three initial leads (four related results per lead). Merge provenance, deduplicate IDs and inspect at most 24 records.
4. Retrieve each record through the authorization and contact-redaction policy, then assess its stated mission, exact terms, concepts, datasets, type and status. Related findings contribute to the assessment.
5. Return up to eight candidates, showing five initially in the interface. Reserve capacity for duplicate, dataset, collaboration and complementary paths. A deterministic relative score combines mission evidence, domain, exact dataset/audience/technology overlaps and status, within lead categories. These are relative leads, not probability scores. The four advisory relationship labels are Potential Duplicate, Strongly Related, Complementary and Weakly Related; legacy lead roles identify datasets, collaborator-seeking and historical records.
6. Compare the two leading assessed projects, read each candidate's approved access information, and evaluate eight reuse constraints. Collect available approved project liaisons for the proposed or inferred domain.
7. Produce an overall path, cited next steps and explicit coverage gaps. Include complementary and dataset actions alongside duplicate investigation when supported.
8. Validate the response schema and persist the completed run to local SQLite. No partial success record is persisted on a tool failure or early cancellation.

Every operation emits a running event before executing and a complete event after returning, with UTC start/end timestamps, elapsed milliseconds, tool name and relevant authorized IDs. Failures emit a failed event and a sanitized error. There are no artificial waits or simulated tool messages. The browser aborts its stream when leaving the page or changing identity. A run that already committed before a disconnect may still exist locally, even if the client did not receive its final result.

## Grounding and uncertainty

Each citation contains `project_id`, `project_name`, local project `url`, `field`, and the actual authorized `value`. Fields can include a mission statement, type, status, datasets, technologies, licensing, access instructions or redacted contacts. Field values are copied from the database view rather than generated by a model. Missing values are represented faithfully, including nulls and empty lists. The interface separates cited catalog fields from its inferred overlap explanation.

Potential duplicates require corroborating mission concepts and exact mission terms, or at least three exact terms covering half of the proposed mission terms. Equipment-failure proposals additionally require a stated failure concept in the candidate mission. An exact dataset-name match can support a relevant data lead. Datasets and retired capabilities have their own classifications; retired status blocks a supported reuse path. Generic semantic similarity alone cannot establish duplication.

The eight constraints are licensing, access, deployment, integration, datasets, support, technology and contact. States are `unknown`, `requires_confirmation`, `potential_mismatch` and `blocking`. Catalog terms and access instructions remain subject to confirmation. A different stated stack is a compatibility question, not proof of incompatibility. A missing POC stays unavailable; the advisor does not invent one.

Overall paths are `investigate_reuse` (potential duplicates), `explore_collaboration` (other active evidence-backed leads), and `continue_discovery` (no active supported lead). The last path does not assert that independent development is safe or that no duplicate exists. Rules are limited in vocabulary, intent and negation handling; users must assess the proposed problem against the cited records.

## API

All routes use the same server-side demo identity policy. The example uses the public visitor; add `X-Demo-User` for an authorized demo identity.

```sh
curl -N http://127.0.0.1:8000/api/v1/agent/discover/stream \
  -H 'Content-Type: application/json' \
  -d '{"description":"Forecast equipment failures from maintenance work orders and supply inventory.","technologies":["Python"],"datasets":["Maintenance work orders"]}'
```

`POST /api/v1/agent/discover/stream` returns newline-delimited JSON (`application/x-ndjson`, `Cache-Control: no-store`):

- `{"type":"run","run_id":"…"}` identifies the new execution.
- `{"type":"activity","activity":{…}}` carries a running, completed or failed operation. Running and completed events share a step number.
- `{"type":"result","run":{…}}` contains the validated, persisted complete assessment.
- `{"type":"error","message":"…"}` terminates a failed stream without exposing internal errors. The HTTP status is already 200 once streaming begins; clients must handle this event and require a result event before claiming completion.

`POST /api/v1/agent/discover` returns a complete JSON `AgentRun` for proposal input, or a grounded question answer for `{"question":"…"}` (see `PHASE2.md`). `POST /api/v1/discovery/check-duplicate` provides the initial-retrieval assessment used by registration, including proposal metadata, ranked evidence components and cited next steps. `POST /api/v1/projects/compare` compares two or three distinct authorized IDs. `GET /api/v1/agent/runs/{id}` reopens an identity-owned run; `/check?run={id}` is its interface route. `/check?project={id}` preloads an authorized project as an editable proposal.

Saved runs include internal fingerprints of the identity scope and authorized inspected records, including contacts. Retrieval rechecks them and returns a 404 if evidence or permissions changed. Fingerprints are private. Catalog writes invalidate saved runs. Snapshots from earlier workflow versions expire when the response contract changes; current runs use version 3.

## Verification

```sh
PYTHONPATH=backend .venv/bin/python -m pytest backend/tests -q
npm --prefix frontend run build
PYTHONPATH=backend .venv/bin/python -m navylink.evaluate
# With make run active:
npm --prefix frontend test
```

Tests verify real related-record expansion; field-by-field citation validity; distinct duplicate and complementary paths; all eight constraint dimensions; current contact and role permissions; progress before execution; sanitized failure events; no partial success on cancellation; local socket-denied execution; no-match behavior; and repeatable labeled evaluations. The browser verifies citation navigation, changing comparison selections, saved-run reload, access denial after identity switching, transport failure, and the complete advisor with external networking blocked.

Reports in `evaluation.json` and `evaluation-neural.json` are small synthetic regression evaluations. Their labels have informed rule development; the scores are not independent evidence of operational accuracy.
